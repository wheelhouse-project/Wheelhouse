# Numbered overlay requirements

Bead: `wh-overlay-refactor-pilot.1` (phase A of the epic `wh-overlay-refactor-pilot`).
Extracted on 2026-11-03 from the design documents, the bead history, and the code at dev `78ad6f76`.

Each requirement states one rule as an input at a Logic process boundary and the output at a boundary.
The inputs are a spoken command, a message from the GUI process, a reply from the Input process,
a Win32 event, the passage of time, or a config value. The outputs are a command to the Input process,
a message to the GUI process, typed words, or no output at all. A private field or a log line is not an output.

## Status values

- **CONFIRMED**: a bead in bd or a design document states the rule as intended, or David confirmed it. Phase A writes boundary tests for these.
- **OPEN**: only the code shows the rule. The question to David is still open. No test is written until he answers.
- **NOT_REQUIRED**: only the code shows the rule, and it needs a short timing window or an unlikely series of events.
  David's rule of 2026-11-04: do not ask him about these. Phase A writes no test, and phase B can keep or change the behavior.
- **NOT_WANTED**: the design states the rule, but David chose to keep today's behavior. No test.

David's rule of 2026-11-04, in his words: "Most of these questions have to do with timing around a 200 MS window.
These are not serious issues. Do not present them to me for adjudication. Do not present anything to me that
requires an extremely unlikely series of events."

## How the labels were checked

- Four read-only extraction passes produced the first labels, one pass for each part below.
- The main session ran `bd show` on all 47 bead IDs that the passes cited. 23 of them have no record in bd.
  These are child beads named only in code comments. A missing bead does not count as confirmation.
  Four requirements lost the CONFIRMED label for this reason: RW-20, RW-22, AO-5, AO-23.
- Seven requirements that the passes labeled CODE_ONLY or CONFLICT cite a bead that exists and states the rule.
  They are now CONFIRMED: LC-22, LC-26, LC-27, LC-28, LC-29, LC-30, CK-48.
- Spot checks against the design document `docs/plans/2026-05-28-voice-element-clicking-phase-1-5-design-v4.md`
  (lines 90, 214, 278-291, 337, 538) and the beads `wh-n29v.111`, `wh-numbers-stay-setting`,
  `wh-overlay-menu-close-stale`, and `wh-n29v.121` agreed with the passes.
- Nothing in the shipped app sends the mic pause or mic resume event to the overlay, so the paused state cannot occur (grep of services/ outside tests and click_overlay_state.py). main.py sends only AUTO_OPEN, BUILD_RESPONSE, CLICK_COMPLETE, FOCUS_CHANGE,
  HIDE_NUMBERS, PAINT_ACK, SHOW_NUMBERS, and TIMEOUT. The requirements of the paused state are CONFLICT for this reason.

## Scope

Phase A covers overlay behavior whose deciding code is in the Logic process: `LogicController` and
`OverlayFocusHookManager` in `services/wheelhouse/main.py`, `click_overlay_state.py`, `overlay_focus_hooks.py`,
and `speech/overlay_click_router.py`. GUI paint rendering and the Input process tree walk are out of scope,
because phase B moves only `LogicController` code. Bare-number badge clicks (a number spoken with no "click")
were not extracted and remain open work.
